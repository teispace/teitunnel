# Local HTTPS domains: verified facts

Collected 2026-09-24 for `crates/localdomains` (M12, decision 7). "Checked locally" means verified on the maintainer's Mac (macOS 27.0, build 26A428) on that date.

## Names and resolution

- **`.localhost`**: RFC 6761 §6.3 says name resolution APIs and libraries should return loopback for `localhost` and every name under `.localhost` without asking DNS. It's a SHOULD, so not every tool does it; browsers and curl special-case it. Source: https://datatracker.ietf.org/doc/html/rfc6761 (read 2026-09-24).
- **macOS system resolver**: `getaddrinfo("app.localhost")` returns `::1` and `127.0.0.1`, and `dscacheutil -q host -a name app.localhost` answers `localhost` → `::1`/`127.0.0.1`. Checked locally. So Safari, curl and anything on the system resolver reach loopback on macOS. (Reports from older Safari versions of `*.localhost` failing exist; not reproducible on this macOS.)
- **Tools that may not resolve `*.localhost`**: they're the reason `resolves_locally()` exists and `.test` is offered. .NET had an open issue about RFC 6761 names in 2025 (https://github.com/dotnet/runtime/issues/118569). glibc's resolver doesn't special-case subdomains of `localhost` unless `nss-myhostname` (systemd) is configured, so Linux tools vary by distro.
- **`.test`** is reserved for testing (RFC 6761 §6.2) and never delegated, so a local responder can't shadow a real site.
- **macOS per-domain resolver**: files in `/etc/resolver/<domain>`; `nameserver` takes an IPv4/IPv6 address and `port` sets the port ("The default port is 53"). Source: `man 5 resolver`, checked locally.
- **systemd-resolved**: `DNS=` accepts an optional port (`111.222.333.444:9953`, `[1111:2222::3333]:9953`), added in systemd 213; `Domains=~example` makes a routing-only domain; drop-ins go in `/etc/systemd/resolved.conf.d/*.conf`. Source: https://manpages.debian.org/testing/systemd-resolved/resolved.conf.5.en.html (read 2026-09-24). Not yet tested on a Linux machine: that a global `Domains=~test` doesn't make the global server a default route for everything else.
- **Windows NRPT**: local rules live under `HKLM\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters\DnsPolicyConfig\<any key name>`; Group Policy rules under `HKLM\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient\DnsPolicyConfig`, and if any GPO rule exists all local rules are ignored. The DNS client caches the table, so after a registry edit it needs `sc control DnsCache paramchange`. Sources: https://www.island.io/blog/man-7-windows-nrpt, https://learn.microsoft.com/en-us/powershell/module/dnsclient/add-dnsclientnrptrule (read 2026-09-24). The rule format has no port field, so the responder must listen on 127.0.0.1:53 on Windows. **Not yet tested on a Windows machine.**
- **mDNS**: `.local` is multicast DNS (RFC 6762). `mdns-sd` answers A/AAAA queries for the host name of every service it registers (read in `mdns-sd` 0.21.4 source, `service_daemon.rs`, `answer_hostname_question`).

## Trust stores

- **macOS**: `security add-trusted-cert` writes the *user* trust domain unless `-d` (admin) is given; `-r trustRoot -p ssl -k <keychain>` limits the trust to SSL. `trust-settings-export` exports the user domain by default (`-d` admin, `-s` system); `remove-trusted-cert` removes user-domain trust. Source: `security <cmd> -h`, checked locally. `find-certificate -Z` prints `SHA-256 hash:` and `SHA-1 hash:` lines (checked locally). The exported plist's `trustList` dictionary is keyed by each certificate's SHA-1 in hex (https://github.com/aosm/Security/blob/master/Security/libsecurity_keychain/lib/SecTrustSettings.cpp). Changing user trust settings shows a password prompt (https://developer.apple.com/forums/thread/671582).
- **Windows**: `certutil [-user] -addstore|-delstore|-store Root <CertId>`; "The `-user` option accesses a user store instead of a machine store"; a CertId can be a serial number or the SHA-1 hash. Source: https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/certutil (updated 2025-10-22, read 2026-09-24). Adding to `CurrentUser\Root` shows Windows' own security warning (well-known behaviour; the dialog comes from CryptoAPI, not certutil).
- **Linux system stores**: Debian/Ubuntu `/usr/local/share/ca-certificates/*.crt` + `update-ca-certificates` (`--fresh` after removal); Fedora/RHEL `/etc/pki/ca-trust/source/anchors/` + `update-ca-trust extract`; openSUSE `/etc/pki/trust/anchors/` + `update-ca-certificates`; Arch (p11-kit) `trust anchor --store|--remove`. All need root.
- **Chrome/Chromium on Linux** reads user-added roots from the NSS shared DB. "Since M146, Chromium defaults to `$HOME/.local/share/pki/nssdb` … If you still have an existing `$HOME/.pki/nssdb` database, Chromium will use that instead." Add with `certutil -d sql:<db> -A -t "C,," -n <nickname> -i <file>` ("C,," = trusted to issue SSL server certificates). Source: https://chromium.googlesource.com/chromium/src/+/main/docs/linux/cert_management.md (read 2026-09-24). NSS `certutil` packages: `libnss3-tools` (Debian/Ubuntu), `nss-tools` (Fedora), `mozilla-nss-tools` (openSUSE), `nss` (Arch, Homebrew).
- **Firefox profiles on Linux**: `~/.mozilla/firefox/*`, snap `~/snap/firefox/common/.mozilla/firefox/*`, Flatpak `~/.var/app/org.mozilla.firefox/.mozilla/firefox/*`, and since Firefox 147 new profiles under `~/.config/mozilla/firefox` (XDG) when no `~/.mozilla` exists. Source: https://www.omgubuntu.co.uk/2026/01/firefox-147-released, https://www.phoronix.com/news/Firefox-147-XDG-Base-Directory (read 2026-09-24).
- **Firefox on macOS/Windows**: since Firefox 120 (November 2023) it imports roots the user or an administrator added to the OS store by default (`security.enterprise_roots.enabled`; Settings > Privacy & Security > Certificates). So installing into the login keychain / `CurrentUser\Root` is enough unless the user switched it off. Sources: https://bugzilla.mozilla.org/show_bug.cgi?id=1848815, https://support.mozilla.org/en-US/kb/setting-certificate-authorities-firefox, https://joshua.hu/mozilla-firefox-trusting-system-root-stores-qwacs-eu (read 2026-09-24).
- **iOS**: after installing a profile with a root certificate, full trust must be enabled in Settings > General > About > Certificate Trust Settings. Source: https://support.apple.com/en-us/102390 (read 2026-09-24).

## Name constraints on a root

- RFC 5280 makes processing name constraints on a trust anchor optional; a dNSName constraint `example.com` matches that name and every name built by adding labels on the left, so `localhost` covers `app.localhost` (the leading-dot form is only defined for URIs and mail addresses). We write `localhost`, `test`, `local`.
- **Chrome**: "Starting with Chrome 112 name constraints will be enforced for user imported trust roots" (Linux changed to match macOS and Firefox), controlled by the `EnforceLocalAnchorConstraintsEnabled` enterprise policy. Sources: https://alexsci.com/blog/name-non-constraint/ (2023-04-01), https://chromeenterprise.google/intl/en_ca/policies/enforce-local-anchor-constraints-enabled/ (read 2026-09-24).
- **Firefox** (mozilla::pkix) enforces constraints on roots; Chrome on macOS (platform verifier) did too before 112. Same source. Netflix's BetterTLS suite found every tested browser rejects the basic case, with Firefox at a 100% pass rate on edge cases: https://netflixtechblog.com/bettertls-c9915cd255c0.
- **rustls/webpki**: rejects a leaf for `evil.com` (and an IP outside the ranges) signed by our constrained root, and accepts `app.localhost`, `*.app.localhost`, `api.test`, `phone.local`, `192.168.1.20`. Checked by `ca::tests::webpki_accepts_local_names_and_rejects_real_sites`.
- rcgen 0.14.10 always marks NameConstraints critical (source `certificate.rs`, `write_x509_extension(…, oid::NAME_CONSTRAINTS, true, …)`), confirmed with x509-parser in `ca::tests::root_has_critical_name_constraints_per_independent_parser`.

## Ports

- **macOS lets a user bind 443 only on the wildcard address.** As a normal user, `bind(127.0.0.1:443)` and `bind([::1]:443)` fail with EACCES, while `bind(0.0.0.0:443)` and `bind([::]:443)` succeed (checked locally, inside and outside the sandbox). This contradicts the plan's "Lens listens on 443/80 on loopback, macOS allows it unprivileged": on macOS Lens has to listen on the wildcard address and drop non-loopback peers (`ports::choose_listener` → `WildcardLoopbackOnly`, `ports::is_loopback_peer`), which also makes LAN mode a filter change rather than a second listener. The macOS firewall may prompt for incoming connections on the wildcard listener.
- Linux reserves ports below `net.ipv4.ip_unprivileged_port_start` (default 1024) for root; fixes are lowering the sysctl or `setcap cap_net_bind_service=+ep <binary>` (lost when the binary is replaced). Windows lets any user bind 80/443 (not re-verified here); `http.sys` or another server may already hold 443.
