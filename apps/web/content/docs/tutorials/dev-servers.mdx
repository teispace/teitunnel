---
title: Share a Vite, Next.js, Django or Rails dev server
description: Fix "Blocked request. This host is not allowed", "Invalid Host header", broken hot reload and CSRF errors when sharing a dev server through Cloudflare Tunnel.
---

Dev servers protect you from DNS-rebinding attacks by refusing requests for hostnames they
don't know. Through a tunnel, requests arrive for `app.example.com` or
`something.trycloudflare.com`, not `localhost`, so the first visit often fails. There are two
fixes; pick one.

## What Teitunnel does for you

- **New shares of Vite, webpack-dev-server and Angular** send the dev server's own address as
  the Host header from the start (`localhost:5173`, say), and the share card says so. Those
  servers only read the Host header to stop DNS rebinding, so nothing else changes. Turn it
  off under **Advanced ▸ Host header** in the share form, or with `--no-host-header`.
- **When a share or route goes live**, Teitunnel fetches it once through Cloudflare, like a
  visitor. If the dev server refuses the address (Vite's *Blocked request*, webpack's
  *Invalid Host header*, Rails' *Blocked hosts*, Django's *DisallowedHost*, or Next.js
  blocking its dev resources), the card or route shows *Your dev server rejects this
  address* with the fix in place: **Send Host: localhost:5173** (a Quick Share restarts with
  a new address; a route changes through a plan like any edit), or **Show the Config Line**
  with the exact line for your framework, ready to copy. After either, it checks again and
  tells you when it works.
- For Next.js, Rails, Django, SvelteKit and Astro the config line comes first: they also
  compare the Host header with the browser's address (server actions, CSRF protection,
  sign-in callbacks), so sending another one can break forms and logins.

`teitunnel share` prints the same finding and suggestion, and keeps sharing (exit status 0).

## Option 1: send `localhost` as the Host header

The quickest fix, with no change to your project. Edit the route (or create it), open
**Advanced ▸ Origin settings** and set **Host header** to `localhost:5173` (your dev server's
address). From the terminal:

```sh
teitunnel route add app.example.com 5173 --host-header localhost:5173
teitunnel share 5173 --host-header localhost:5173
```

Your dev server then sees every request as a request for itself. This works for most
setups; the catch is that anything the app builds from the Host header (absolute links,
redirects, OAuth callbacks) says `localhost` too, and frameworks that compare it with the
browser's `Origin` (Next.js server actions, Rails and Django CSRF checks, SvelteKit form
actions) reject form posts. If that matters, use option 2.

## Option 2: allow the hostname in your project

<Tabs items={["Vite", "Next.js", "Django", "Rails", "webpack", "Laravel"]}>
  <Tab value="Vite">
    Vite 6.0.9 and later (and 5.4.12, 4.5.6) answer *Blocked request. This host
    ("app.example.com") is not allowed.* Allow your hostname in `vite.config.ts`:

    ```ts
    export default defineConfig({
      server: {
        allowedHosts: ["app.example.com"], // or [".trycloudflare.com"] for Quick Shares
        hmr: { clientPort: 443 },           // hot reload through the tunnel
      },
    });
    ```

    A leading dot allows every subdomain. `hmr.clientPort: 443` makes the browser open the
    hot-reload WebSocket on the tunnel's HTTPS port instead of `5173`, so edits show up live
    for everyone viewing it. The same `server` options work for SvelteKit, Astro, Nuxt, Remix
    and other Vite-based frameworks.
  </Tab>
  <Tab value="Next.js">
    `next dev` serves pages to any host, but newer versions warn about, and will block,
    cross-origin requests to dev-only resources such as hot reload. Allow your hostname in
    `next.config.js`:

    ```js
    module.exports = {
      allowedDevOrigins: ["app.example.com", "*.trycloudflare.com"],
    };
    ```
  </Tab>
  <Tab value="Django">
    Django answers *Invalid HTTP_HOST header* (400) and, for forms, *CSRF verification failed*
    (403). In `settings.py`:

    ```py
    ALLOWED_HOSTS = ["localhost", "127.0.0.1", "app.example.com"]
    CSRF_TRUSTED_ORIGINS = ["https://app.example.com"]
    ```

    `CSRF_TRUSTED_ORIGINS` needs the scheme (`https://`) since Django 4.0.
  </Tab>
  <Tab value="Rails">
    Rails shows *Blocked hosts: app.example.com*. In `config/environments/development.rb`:

    ```rb
    config.hosts << "app.example.com"
    config.hosts << ".trycloudflare.com" # every Quick Share address
    ```
  </Tab>
  <Tab value="webpack">
    webpack-dev-server (and Create React App, Vue CLI, Angular) answers *Invalid Host
    header*. In `webpack.config.js`:

    ```js
    module.exports = {
      devServer: {
        allowedHosts: ["app.example.com"], // or "all"
        client: { webSocketURL: "auto://0.0.0.0:0/ws" },
      },
    };
    ```
  </Tab>
  <Tab value="Laravel">
    `php artisan serve` accepts any host. If assets or links point at `http://localhost`,
    set `APP_URL=https://app.example.com` in `.env`, and trust the tunnel as a proxy so
    Laravel knows the page is HTTPS (`$middleware->trustProxies(at: '*')` in
    `bootstrap/app.php` on Laravel 11). With Vite, also follow the Vite tab.
  </Tab>
</Tabs>

## Streaming (Server-Sent Events) and MCP servers

Quick Shares (`trycloudflare.com` addresses) don't carry Server-Sent Events: the stream never
reaches the browser. When the service answers with `text/event-stream` (a streaming UI, or an
MCP server on the SSE transport at `/sse`), the share card says so. Share it on your own
domain instead (**Address ▸ On example.com**, or `teitunnel share 3000 --on
demo.example.com`), where streams work.

## HTTPS dev servers

If your dev server itself uses HTTPS with a self-signed certificate (`https://localhost:8443`),
cloudflared refuses it by default. Turn on **Origin settings ▸ No TLS verify** for the route,
or `--no-tls-verify` on the command line. Visitors still get Cloudflare's valid certificate.

## Mixed content and redirects

Visitors reach your app over HTTPS, but your app receives plain HTTP from cloudflared. If it
builds `http://` links or redirects HTTP to HTTPS forever, tell it to trust the proxy headers
(`X-Forwarded-Proto: https`): `app.set("trust proxy", true)` in Express,
`SECURE_PROXY_SSL_HEADER` in Django, `config.assume_ssl = true` in Rails 7.1+. See
[too many redirects](/docs/reference/troubleshooting#too-many-redirects).
